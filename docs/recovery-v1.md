# Recovery Middleware v1

## 目标

Policy 负责判断工具调用能不能执行；Recovery 负责工具已经执行失败后，判断是否值得重试、是否应把错误交回 Agent，以及是否已经进入重复调用循环。

## 第一版行为

| 失败类型 | 处理 |
|---|---|
| 超时、连接重置、暂时不可用 | 最多重试一次 |
| Policy 拒绝、预算耗尽 | 不重试，记录终止事件 |
| 普通参数或工具错误 | 不盲目重试，把错误交回 Agent |
| 相同工具和参数重复超过 2 次 | 阻断并返回恢复错误 |

Recovery 不会对所有错误自动重试。对路径错误或 Policy 拒绝重复调用同一个请求通常没有意义，反而会浪费预算并形成循环。真正的修复需要让模型看到错误后生成新的工具参数；这一点将在后续故障注入任务中验证。

## 事件

Recovery 写入以下事件：

- `recovery_failure`：记录分类、工具名和尝试次数；
- `recovery_retry`：决定再次尝试；
- `recovery_success`：工具最终成功；
- `recovery_terminal`：错误不可重试或重试耗尽；
- `recovery_loop_blocked`：重复调用被阻断。

## 你需要掌握的工程结论

Recovery 不是简单的 `try/except`。它至少需要错误分类、重试上限、循环检测和可观察事件。Policy 错误和暂时性连接错误必须走不同路径，否则系统会不断重复一个明确被禁止的操作。

本轮已经完成 middleware 契约、工具超时重试、错误参数纠正和注入测试失败的 Agent 图场景。下一步是为 Checkpoint/Replay 设计稳定的事件和状态格式。
