# 基线测试门对照实验 v1

## 实验问题

这次实验研究的不是业务代码本身，而是一个 Harness 规则是否改变 Agent 的执行顺序：

> 强制 Agent 先运行基线测试，是否能让“测试失败后纠错”变成可观察证据？

两组使用同一个 `normalize-title` fixture、同一个 DeepSeek 模型和同一个隐藏测试，唯一变量是 `require_baseline_test`。

## A/B 设计

| 组别 | 基线测试门 | 允许编辑的时机 |
| --- | --- | --- |
| A | 关闭 | 第一次测试前也可以编辑 |
| B | 开启 | 第一次 `run_tests` 完成后才能编辑 |

隐藏测试位于 workspace 外，Agent 不能修改测试文件。

## 结果

### A 组：关闭基线测试门

运行目录：[20261107T033410Z-62d4686f](../runs/recovery/20261107T033410Z-62d4686f/)

```text
模型读取代码
  ↓
直接修改 title_utils.py
  ↓
第一次隐藏测试：2 passed
```

结果：

- `baseline_gate=false`；
- `Policy` 拒绝次数为 0；
- 只运行一次测试，第一次就通过；
- 产生了生产代码 diff。

这证明模型能修复任务，但不能证明它是根据失败测试进行纠错。

### B 组：开启基线测试门

运行目录：[20261106T121015Z-8c84a761](../runs/recovery/20261106T121015Z-8c84a761/)

```text
模型尝试编辑
  ↓
Policy 拒绝
  ↓
第一次隐藏测试：2 failed
  ↓
模型修改 title_utils.py
  ↓
第二次隐藏测试：2 passed
```

结果：

- `baseline_gate=true`；
- `Policy` 拒绝提前编辑 1 次；
- 第一次测试失败；
- Recovery 记录失败并终止本次自动重试；
- 模型修改生产代码后，第二次测试通过。

## 对照结论

| 指标 | A 组：无门 | B 组：有门 |
| --- | --- | --- |
| 首次测试 | 通过 | 失败 |
| 测试次数 | 1 | 2 |
| Policy 拒绝 | 0 | 1 |
| 是否能证明失败后纠错 | 不能 | 能 |
| 最终测试 | 通过 | 通过 |

最终结果相同，但证据质量不同。A 组只能说明“模型修改后通过测试”，B 组才能说明“模型看到失败后修改并通过”。

## 学习结论

1. A/B 实验必须只改变一个变量，否则无法把结果差异归因于基线测试门。
2. 最终成功率相同，不代表 Harness 的可观察性和实验价值相同。
3. 基线测试门不是提高业务代码正确率的魔法，它的主要作用是强制并记录一个可分析的执行顺序。
4. A 组日志中出现的 `ls` 路径错误与业务测试无关，应单独分类，不能误算为 Recovery 成功或失败。

## 限制

这只是一个任务、一个模型和一次 A/B 对照。模型输出具有随机性，后续需要重复运行或增加任务，才能估计门控规则对恢复率的稳定影响。旧 B 组运行是在测试事件修复前生成的，因此 `run.json.test_runs` 能证明第一次测试失败，但旧 `events` 没有准确写入对应的 `recovery_failure`；报告将这两类证据分开显示。
