# 评测与失败分类 v1

## 实验目标

Baseline 已经有 10 个任务和多次运行记录。本阶段要回答：

> Agent 的任务能力、模型服务稳定性和本机运行环境，应该如何分开统计？

如果把所有 `run.json` 只按最后是否成功计算，会把连接失败、额度失败和模型配置错误误判成代码 Agent 的失败，也会隐藏重试次数。

## 设计选择

评测器位于 `evals/report.py`，逐个读取 `runs/<run-id>/run.json`，只在内存中保留每次尝试的短摘要：任务 ID、模型、分类、测试次数、事件数量和 diff 字符数。完整消息和 diff 仍保留在磁盘，因此历史记录增加不会按比例占用运行内存。

报告同时给出两个分母：

| 指标 | 分母 | 用途 |
| --- | --- | --- |
| 全部尝试成功率 | 所有可解析运行 | 观察实际运行稳定性，包括模型服务失败 |
| 有效尝试成功率 | 排除模型、初始化和损坏产物问题 | 观察 Agent 在真正开始执行后的任务表现 |

每个任务还保留：

- `latest_attempt`：该任务最新一次尝试；
- `latest_valid_attempt`：排除基础设施问题后的最新尝试。

这样既不丢失历史，也不会让一次连接失败覆盖掉任务真正的执行结果。

## 失败分类

当前分类为：

```text
success
test_failure
model_error
setup_error
agent_error
invalid_artifact
```

本版根据 `execution_error` 和结果字段分类。没有生成 `run.json` 的初始化失败无法从现有目录推断，因此这类失败仍需要后续加入 setup manifest 才能完整统计。

## 实际结果

使用现有 `runs/` 目录生成的报告：

```text
运行尝试数：14
任务数：10
成功尝试数：11
全部尝试成功率：78.6%
有效尝试数：11
有效尝试成功率：100.0%
model_error：3
success：11
```

按每个任务的最新有效尝试统计：

```text
10/10 任务成功
```

这组数字应该这样解释：11 次是真正完成 Agent 任务并通过测试，3 次在模型服务阶段失败；不能把它们合并成“Agent 失败”，也不能只报告 100% 而隐藏 78.6% 的真实尝试稳定性。

报告文件：

- [baseline-summary.json](../evals/reports/baseline-summary.json)
- [baseline-summary.md](../evals/reports/baseline-summary.md)

重新生成报告：

```powershell
python -m evals.report --runs-dir runs --output-dir evals/reports
```

## 学到的工程结论

1. 评测首先要定义分母，否则同一批运行可以产生看似矛盾的成功率。
2. “最新有效运行”适合回答任务当前能力，“全部尝试”适合回答系统稳定性。
3. 评测器应读取已有产物，不应该为了统计结果再次调用模型。
4. 运行产物保留在磁盘，聚合器只保留短摘要，可以同时满足可追溯性和内存控制。
5. 没有 `run.json` 的 setup failure 不能凭空从成功运行矩阵推导出来，需要单独的初始化错误记录。

## 当前限制和下一步

10 个任务都来自很小的计算器项目，且有效运行没有 `test_failure`。因此当前报告能证明运行记录和失败分类机制工作，不能证明 Recovery 对真实代码错误的修复能力。

下一步应加入受控故障注入任务：先让测试失败或工具参数错误，再观察模型是否修改代码或参数、Recovery 事件是否正确、最终结果是否恢复成功。
